## 3. 실행 순서와 실패 대처

1. 페이블에 [검토 프롬프트](FABLE_ALL_REMAINING_SLOTS_PROMPT_20260907.md)를 전달한다. 현재 직접 연결된 페이블 실행 도구/태스크는 확인되지 않았으므로 사용자 전달 방식이며, 전달/응답 완료로 표기하지 않는다.
2. Codex는 준비된 P3-A의 source/answer/QA 지문 및 현 quota를 확인하고, P1/P2/P3-B의 기존 자산과 중복 여부를 read-only 점검한다. 페이블 답변을 기다리는 동안 기존 P3 학습을 변경하지 않는다.
3. 새 후보별 사전등록 → 필요한 실제 학습(또는 source에서 재생 가능한 모델 재사용) → 내부 비교 → 별도 PID replay → 답안 key/order/schema/finite/hash/기존 제출 중복 QA → 리더보드 제출 → 화면 채점·정확한 SHA receipt.
4. 각 문제에서 한 후보가 실패/평균 악화했다고 그 문제 전체를 중단하지 않는다. 다음 사전등록 독립 변경 또는 정보 가치 후보로 이어간다. 학습 불변 attempt의 기술 실패는 보존하고 새 ID로만 처리한다. 규정/접근권한 충돌은 우회하지 않는다.
5. 모든 합법적 슬롯 활용 후 최종 후보 결정표 작성: 각 후보의 Public 점수, 내부 평균·위험, source-only/저장 모델 재현 범위, 적격성 미확인 사항을 함께 둔다. 악화 분기 하나가 자동 탈락 기준은 아니며, 재현 불일치를 최고 Public 점수로 숨기지도 않는다.
6. 선택 버전별 독립 final-release 폴더를 구성: 데이터 참조 / 소스·설정 / 학습 결과 / 로그·환경·QA / 답안 / README·FORM. 기존 fallback/실패 증거를 덮어쓰지 않는다.
7. 학습→모델→답안의 동일성, SOURCE_ONLY/SAVED_MODELS, 50MB 파일 제한에 맞춘 분할·재조립 SHA, 문서·FORM·채점 CSV SHA 일치 확인. 전부 소모하기 전에도 fallback 사전 포장은 가능하나, 최종 지정은 그 뒤다.
8. 사용자 목표 범위에서 **공식 모델 최종 제출 및 제출관리 접수 확인**. 포털에 필요한 미확인 필드/규정 충돌은 구체적으로 알린다. 업로드 응답이 불확실하면 재클릭 전에 접수를 확인한다.
